Česky

C09 — Implementace změny, integrace, CI a reprodukovatelný release

1. Od schválené změny k ověřené verzi

V C08 jste stanovili přesnou before baseline, přijatý změnový požadavek, analýzu dopadu, varianty a review rozhodnutí. C09 uzavírá cestu od rozhodnutí k ověřené a identifikované verzi produktu. Pokud bylo zvoleno ACCEPT, implementujte nejmenší schválenou změnu, zrevidujte ji a proveďte nové i regresní testy. Pokud jste na základě skutečných důkazů rozhodli REJECT/NO_CHANGE, nevymýšlejte umělý commit: reprodukujte nezměněnou přijatou baseline, doložte zachovaná pravidla a přezkoumanou alternativní reakci. Pouhé DEFER bez dalšího rozhodnutí nebo chybějících podkladů nestačí.

Technický postup: accepted CR → branch/patch → code review → build → unit + relevant real integration test → CI feedback → clean checkout → artefakt, konfigurace a schéma → release candidate decision. CI green znamená jen to, že prošly provedené kontroly; není synonymem verifikace všeho ani povolením nasazení.

Vlastní změna týmu: použijte právě ten Change Request a zvolenou variantu, které jste skutečně posoudili a rozhodli v C08. Následující CR-08 je pouze vypracovaný příklad postupu, nikoli povinná funkcionalita vašeho systému.

2. Výsledek a realistický rozsah

Výstupem je jeden jasně identifikovaný release candidate či dokumentované HOLD, ne cloudová infrastruktura. Použijte aktuální jazyk a tooling, které máte. Požadujeme: identifikovaný before/after commit/tag (i stejné při NO_CHANGE), spustitelné build/test instrukce, výsledek review, nové a regresní testy navržené v C08, nyní skutečně provedené, nejméně jednu skutečnou integrační hranici a čistou reprodukci jiným členem. CI job při push/PR použijte tam, kde je dostupný; pokud není, doložte automatizovaný script a důvod omezení. Není předepsán Kubernetes, Docker, GitHub, GitLab ani cloud.

Rozpracované kroky dokončete do příštího cvičení. Doložte skutečný výsledek; neprovedené testy označte NOT RUN, skutečnou překážku BLOCKED s příčinou a dalším proveditelným krokem.

Podrobné vysvětlení jednotlivých kroků

Krok 0 — Převzít rozhodnutí z C08

Otevřete svou Change Card z C08. Najděte přesný požadavek a jeho acceptance criteria, zvolenou variantu, zdůvodnění rozhodnutí a commit, na kterém analýza vznikla. Zkontrolujte, že rozhodnutí skutečně znamená ACCEPT. Pokud je podmíněné, vyjasněte podmínky před úpravou kódu. Pokud je NO_CHANGE/REJECT, pokračujete ověřením nezměněné baseline a svého zdůvodnění, nikoli umělou změnou.

Příklad: C08 stanovilo, že po vypršení potvrzovací lhůty nelze rezervaci potvrdit. Záznam musí říci, zda se při přesně 30:00 ještě potvrzuje, nebo již zamítá; bez toho nelze napsat správný test. Hotovo, když lze ukázat Change Card, rozhodnutí a původní commit, bez dalšího vymýšlení požadavku.

Krok 1 — Vymezit nejmenší skutečnou změnu

Z Impact Matrix určete, které konkrétní části stávající aplikace se mění: vstupní API, aplikační pravidlo, stavový přechod, databázový zápis, konfigurace nebo test. Ke každému dopadu napište, co se mění a co má zůstat stejné. Položku N/A používejte jen se stručným zdůvodněním. Nejde o tvorbu nové architektury; jde o výběr rozsahu a regresních rizik.

Příklad: Změna validace času v Approve může zasáhnout serverové pravidlo, časový zdroj a testy, ale nemusí vyžadovat nové tabulky. Hotovo, když je zřejmé, na co má implementace sáhnout a které dřívější chování se nesmí změnit.

Krok 2 — Implementovat přijaté rozhodnutí

Vycházejte z identifikované baseline. Pro ACCEPT vytvořte kontrolovatelnou úpravu kódu, případných migrací a souvisejících specifikací; rozlište ji jednoznačným commitem nebo PR. Změnu udržte v mezích schváleného řešení. Pokud při implementaci narazíte na nový zásadní dopad, vraťte ho do rozhodnutí, místo abyste potichu rozšířili zadání. Pro doložené NO_CHANGE žádný nový funkční commit nutný není.

Příklad: Kontrola expirace se provádí na serveru před potvrzujícím databázovým přechodem; nestačí skrýt tlačítko ve webovém rozhraní. Hotovo, když lze ukázat konkrétní diff a commit a vysvětlit, jak odpovídají schváleným AC.

Krok 3 — Zrevidovat změnu a skutečně provést testy

Jiný člen porovná diff s přijatými AC: zkontroluje normální cestu, hranici, zamítnutí, data a možné souběhy. Potom spusťte nové testy změny i relevantní regresní testy z C08. U každého evidujte předem určené expected, skutečné actual, výsledek a příkaz/commit. Alespoň jedna zkouška musí projít skutečnou integrační hranicí (například aplikace–testovací DB), nejen mockem. Pro stavový požadavek ověřte také perzistovaný stav samostatným čtením.

Příklad: Při 29:59 se očekává povolené potvrzení a v nové DB transakci stav CONFIRMED; při ilustrační hranici 30:00 se očekává zamítnutí a DB nesmí obsahovat chybně potvrzenou rezervaci. Hotovo, když existují skutečné, dohledatelné výsledky, nikoli jen napsané test cases.

Krok 4 — Automatizovat sestavení a kontroly

Zapište opakovatelný postup, který spustí instalaci či kontrolu závislostí, build a relevantní automatizované testy. Ideálně ho připojte k existujícímu CI workflow při push/PR; pokud tým CI nemá, připravte jeden spustitelný lokální script a výslovně uveďte omezení. Zaznamenejte commit, prostředí, konkrétní příkaz, exit code a odkaz na log. Ujistěte se, že se integrační test opravdu spouští v tomto procesu, nikoli jen jednotlivě na autorově notebooku.

Příklad: Pro Maven může jít o ./mvnw clean verify, ale pouze pokud projekt skutečně obsahuje potřebné integrační testy a konfiguraci. Samotný zelený status neprokazuje netestované cesty. Hotovo, když jiný člen umí spustit stejnou kontrolu a je vidět, co se provedlo.

Krok 5 — Ověřit reprodukovatelnost na čistém checkoutu

Druhý člen týmu v novém adresáři získá přesný commit, postupuje jen podle README, připraví deklarované prostředí a testovací data, spustí build, testy a start/smoke check. Autor nesmí problém opravit nezdokumentovanou lokální konfigurací. Zapište operační systém/runtime, potřebné proměnné bez tajných hodnot, příkazy, skutečný výsledek a případný blocker.

Příklad: Pokud aplikace funguje jen díky lokálnímu .env, který není popsán, clean checkout neprošel. Doplnění dokumentovaného příkladu konfigurace a nový pokus jsou součástí nápravy. Hotovo, když lze sestavení a kontrolu zopakovat, nebo je přesně doloženo, proč zatím ne.

Krok 6 — Určit, co přesně je kandidátem na vydání

Pojmenujte výsledný commit/tag a sestavený artefakt (soubor, verze nebo hash), runtime, uzamčené závislosti, databázové schéma/migrace a netajnou konfiguraci. Zaznamenejte, které testy skutečně běžely a jaká omezení zůstávají. Napište, co by obnášelo vrácení aplikace; rollback kódu sám nevrátí změněná databázová data. Není nutné nasazení do cloudu ani složitá release platforma.

Příklad: commit 9d25c41, JAR či jiný artefakt vytvořený z tohoto commitu, deklarovaná DB migrace a testovací log. Hotovo, když by další člověk poznal, jakou konkrétní verzi a za jakých podmínek má zkoušet.

Krok 7 — Rozhodnout podle důkazů, ne podle dojmu

Porovnejte skutečné výsledky s přijatými kritérii a s původními invariants. Rozhodnutí READY je opřené o dokončené relevantní kontroly, CONDITIONAL přesně popisuje omezení a podmínky, HOLD znamená konkrétní otevřené selhání či nedostatek důkazů. Zapište, kdo za rozhodnutí v týmu odpovídá, proč ho učinil a co by bylo potřeba k jeho změně. Zelená CI automaticky nedává souhlas k nasazení.

Příklad: Nové AC i regrese prošly, ale clean checkout druhého člena selhal kvůli nezdokumentované DB konfiguraci → HOLD, oprava README a opakování reprodukce. Hotovo, když lze rozhodnutí obhájit konkrétními výsledky a odkazy.

4. Vyplněný příklad: CR-08 expiry kontrola

Příklad používá předchozí C08 změnu: po 30 minutách se čekající žádost nemůže potvrdit; tým schválil lazy expiry při pokusu o Approve. Nejprve doplňte skutečné acceptance podmínky k výslednému návrhu, např. AC-01 schválení v 29:59 při splněných podmínkách, AC-02 pozdní zamítnutí v 30:01, AC-03 přesnou hranici 30:00 podle explicitně dohodnuté inkluzivity (v tomto ilustračním příkladu se přesně 30:00 již zamítá; věk ≥ 30:00), AC-04 regresi BR-02 (žádný překryv dvou CONFIRMED). Nepřijímejte očekávání podle toho, co nový kód zrovna dělá.

5. CI, závislosti a reprodukovatelný checkout

V README uveďte přesné příkazy pro závislosti, schéma, test DB, build/test/run a smoke. Typové ukázky: ./mvnw clean verify nebo npm ci && npm test nebo pytest; nejde o požadované technologie. CI workflow minimálně identifikuje commit/PR, prostředí, kroky, exit status a dostupný log. Integrační test musí používat skutečnou relevantní hranici (např. testovací DB), nikoli jen in-memory mock. Tajné klíče nejsou součástí evidence; jejich konfiguraci popisujte jako požadované proměnné.

Clean checkout pokus: druhý člen v novém adresáři získá přesný commit/tag, podle README nastaví neautentizační konfiguraci, připraví DB, spustí test a aplikaci. Zaznamenejte čas, prostředí, příkaz, očekávání a actual. Selže-li to, výsledek je FAIL/BLOCKED s důvodem a opravou; není přípustné tvrdit „reprodukovatelné“, když musel autor nezdokumentovaně doplňovat soubory.

Release identity: kód + lockfile/verze závislostí + runtime + schéma/migrace + ne-tajná konfigurace + vytvořený artefakt/tag/digest + skutečné test evidence. Rollback aplikace nevrací automaticky databázová data, proto popište omezení či ověřenou strategii obnovy.

7. Definition of Done

  • Vazba na jedno skutečně reviewed rozhodnutí C08; implementovaná schválená změna nebo důkazově plnohodnotné NO_CHANGE, nikoliv účelově vymyšlený REJECT.

English

C09 — Implementing the change, integration, CI and reproducible release

1. From an approved change to a verified product version

C08 established the exact before baseline, a credible request, impact analysis, alternatives and a reviewed decision. C09 closes the path from decision to verified, identified product state. If the decision was ACCEPT, implement the smallest approved change, review it and execute new and regression tests. If a defensible REJECT/NO_CHANGE was accepted, do not invent a code delta: reproduce the unchanged baseline, show the preserved claims and the feasible compensating response. A bare DEFER without the needed decision evidence is insufficient.

Engineering sequence: accepted CR → branch/patch → review → build → unit + real integration check → CI feedback → clean checkout → artifact/schema/config identity → release candidate decision. Green CI only proves the checks that actually ran, not total correctness or authorization to deploy.

Your team's change: continue with the actual Change Request and approved option reviewed in C08. The CR-08 below is a worked example of the method, not a mandatory new feature for your system.

2. Outcome and fair scope

Produce one identified release candidate or documented HOLD, not a cloud platform. Reuse your current stack. Evidence includes before/after commit/tag (possibly identical for no-change), executable build/test instructions, review, new and regression tests designed in C08, now executed, at least one real integration boundary, and a clean reproduction by a different team member. Use push/PR CI if accessible; otherwise provide an automatable script plus the reason for the limitation. Kubernetes, Docker, GitHub, GitLab and cloud hosting are not mandatory.

Complete unfinished work before the next exercise. Report actual evidence; use NOT RUN for tests not executed and BLOCKED for a real obstacle, its cause and a feasible next action.

Detailed explanation of each step

Step 0 — Take over the reviewed C08 decision

Open your C08 Change Card. Locate the exact requirement and acceptance criteria, selected option, rationale and source commit used for impact analysis. Check that the reviewed disposition is genuinely ACCEPT; resolve any stated conditions before coding. For an evidence-backed NO_CHANGE/REJECT, verify the unchanged baseline and rationale rather than fabricating code changes.

Example: A 30-minute confirmation window needs an explicit outcome at exactly 30:00; without that rule, no independent expected test result exists. Complete when: the Change Card, decision and before-commit are directly traceable.

Step 1 — Bound the smallest real delta

Use the C08 Impact Matrix to identify the specific parts of your existing system that may change: API, business rule, state transition, persisted data, configuration or tests. Say what changes and what is intentionally unchanged. Mark something N/A only with a short reason. Do not design a replacement architecture; bound the implementation and its regression exposure.

Example: Server-side approval time checking may affect a handler, clock source and tests without requiring a database migration. Complete when: scope and unchanged behavior are explicit.

Step 2 — Implement the accepted option

Start from the identified before-baseline. For ACCEPT, make a version-controlled change to code and any affected migration/specification, with a traceable commit or PR. Keep the change inside the approved option. If an important new effect appears, return it to decision review rather than silently expanding scope. Defensible NO_CHANGE does not need a synthetic implementation commit.

Example: Enforce expiration server-side before the confirming persistent transition; hiding a client button is insufficient. Complete when: the diff and commit can be mapped to the accepted criteria.

Step 3 — Review and execute real tests

A teammate challenges the diff against acceptance criteria, including normal path, exact boundary, rejection path, persistence and concurrency where relevant. Execute new behavior tests and C08 regression tests, recording predeclared expected, observed actual, verdict, command and commit. At least one check must cross a real integration boundary (for example, service to test database), not just a mock. For stateful claims independently read committed state.

Example: At 29:59 approval may produce independently confirmed persisted CONFIRMED; at illustrative 30:00 rejection must leave the record not confirmed. Complete when: real evidence and test runs exist, not just authored test cases.

Step 4 — Automate the build and checks

Write a repeatable command or script that handles dependency preparation, build and relevant automated tests. Wire it into an existing push/PR CI workflow if available; otherwise use an executable local automation script and document that limitation. Capture commit, environment, command, exit code and log. Ensure the real integration check belongs to this automated run rather than being an undocumented manual step.

Example: ./mvnw clean verify is suitable only if the project actually configures the intended integration tests. A green job does not cover absent tests. Complete when: another teammate can run the same check and see which tests executed.

Step 5 — Reproduce from a clean checkout

A different team member clones or checks out the exact commit into a new directory and follows only the README to prepare the declared environment and test data, build, test and start/smoke-check the service. Undocumented author-only fixes are not allowed as evidence of reproducibility. Record OS/runtime, required nonsecret environment variable names, exact commands, observed results and any blocker.

Example: If the run requires an unmentioned local .env, the clean checkout failed. Document the config and retry. Complete when: independent reproduction passes or the failure and next action are precisely evidenced.

Step 6 — Identify the release candidate

Record the resulting commit/tag and built artifact (filename, version or hash), runtime, pinned dependencies, database schema/migrations and nonsecret configuration. Attach real checks and known limitations. Describe how application rollback would work and remember that rolling back code does not automatically undo stored database changes. A cloud deployment is not required.

Example: Commit 9d25c41, an artifact built from that commit, declared DB migration and matching test log. Complete when: another engineer can identify exactly what would be tested or delivered.

Step 7 — Make an evidence-based decision

Compare the actual evidence with the accepted criteria and unchanged invariants. READY requires relevant completed checks, CONDITIONAL states limitations and conditions, and HOLD names failed checks or missing evidence. Record who takes responsibility, the rationale and what would change the decision. Green CI is not deployment authorization.

Example: All acceptance and regression tests pass, but a second member's clean checkout fails because database configuration was undocumented → HOLD, repair README and rerun. Complete when: the decision can be defended with actual results and source links.

5. CI, dependencies and clean reproduction

Write exact README commands to install dependencies, set up a test DB/schema, build, test, run and smoke. Illustrations include ./mvnw clean verify, npm ci && npm test, or pytest, depending on the existing project. A pipeline records tested commit/PR, environment, commands, exit codes and logs. A meaningful integration check crosses a real boundary such as a test DB, not only a mocked repository. Describe required secret variables without publishing actual credentials.

Clean checkout: another team member obtains the exact tag/commit in a new directory, follows the README and known harmless configuration, prepares data and executes build/tests/run. Record environment, command, expected and actual. If they need undocumented personal files or manual author intervention, the result is FAIL/BLOCKED with a corrective action, not “reproducible.”

Release identity combines source, resolved dependency versions/lock, runtime, database schema/migration, nonsecret config, built artifact/tag/digest and actual check results. Reverting application code does not automatically reverse database changes; document a tested recovery or a candid limit.
