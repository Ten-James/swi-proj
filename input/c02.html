Co je cílem

V C01 jste určili, jaký rezervační systém stavíte. V C02 musíte přesně popsat a odsouhlasit celé jeho minimální chování: vytvoření rezervace, zjištění dostupnosti, potvrzení rezervace a její zrušení.

Výsledkem nemá být „dokument s požadavky“. Výsledkem má být specifikace, které tým rozumí a za kterou dokáže převzít odpovědnost, plus jednoduchá spustitelná aplikace vytvořená s pomocí AI, jejíž chování této specifikaci odpovídá.

V C03 vezmete právě tuto aplikaci a budete řešit její architekturu. Proto v C02 neoptimalizujte strukturu kódu dopředu.

Co si máte odnést: AI může navrhnout požadavky, diagramy, testy i kód. Vy musíte být schopni u každého přijatého požadavku vysvětlit co přesně znamená, proč je potřeba, kdy platí, co by ukázalo jeho porušení a jak poznáme, že jej systém splňuje.
Vztah k CP1: C02 vytváří především část Požadavky + evidence. C03 přidá architekturu a upraví běžící základ do obhajitelného walking skeletonu. Stav pro CP1 se zmrazí po C03 a kontroluje během C04. C02 tedy není samostatný projekt vedle CP1 — je jeho součást.

C02 předpokládá dokončený C01. Project Frame, zvolenou doménu rezervačního systému, repozitář, C01 spike ani definici walking skeletonu znovu nevytvářejte.

A. Baseline v0.1 — specifikujte celý minimální systém

1. Čtyři základní operace

Zpracujte všechny následující operace. Názvy můžete přizpůsobit své doméně, jejich význam ale musí zůstat jednoznačný:

  1. Create Reservation — vytvoření návrhu nebo žádosti o rezervaci.
  2. Check Availability — zjištění, zda je Resource v požadovaném intervalu dostupný.
  3. Confirm Reservation — okamžik, kdy systém rezervaci přijme jako platnou alokaci Resource.
  4. Cancel Reservation — zrušení existující rezervace podle přijatých pravidel.
Pozor na význam: „Create“ automaticky neznamená, že Resource už je skutečně rezervován. „Cancel“ automaticky neznamená fyzické smazání dat. Operace `Approve` zatím není součástí základního modelu — objeví se až po změně, pokud nový proces skutečně vyžaduje schvalování.

4. Podrobný referenční příklad — Create Reservation

Příklad odpovídá běžnému systému s exkluzivním Resource. Vlastní doménu přizpůsobte, ale zachovejte stejnou úroveň přesnosti.

Ukázka specifikace je záměrně anglicky.

## OP-01 — Create Reservation

Goal / user value:
User creates a reservation request that can later be confirmed.

Trigger:
Authorized User requests a Reservation for Resource R and interval I.

Observable requirement:
REQ-01:
The system shall create a DRAFT Reservation for an existing Resource
when the requested interval is valid.

Preconditions:
- User is authorized to create Reservations.
- Resource exists.
- start < end.

Success postcondition:
- one new Reservation exists;
- Reservation.state = DRAFT;
- no Resource allocation is committed yet.

State change:
[none] → DRAFT

Referenced rules:
BR-01 Interval semantics.

Main success scenario:
1. User submits Resource and interval.
2. System validates authorization, Resource and interval.
3. System creates Reservation in DRAFT.
4. System returns the Reservation identifier and current state.

Alternative / failure outcomes:
- unauthorized User → reject; no Reservation created;
- unknown Resource → reject; no Reservation created;
- invalid interval → reject; no Reservation created.

Verification examples:
valid Resource + [10:00,11:00) → one DRAFT created
start == end → rejected
unknown Resource → rejected

Rationale:
Creation records user intent without committing Resource allocation.
Důležitý význam: v tomto příkladu se při Create nekontroluje kolize rezervací, protože stav DRAFT ještě Resource nealokuje. Tým může zvolit jinou politiku, ale musí ji explicitně popsat a používat konzistentně. AI toto rozhodnutí nesmí udělat potichu za vás.

5. Podrobný referenční příklad — Check Availability

Ukázka specifikace je záměrně anglicky.

## OP-02 — Check Availability

Goal / user value:
User can determine whether an exclusive Resource is currently
available for a requested interval.

Observable requirement:
REQ-02:
For a valid interval, the system shall report a Resource as unavailable
if the interval overlaps any CONFIRMED Reservation of that Resource;
otherwise it shall report it as available.

Preconditions:
- Resource exists.
- requested interval is valid.

Success postcondition:
- availability result is returned;
- no Reservation state is changed.

Referenced rules:
BR-01 Interval semantics.
BR-02 Exclusive Resource invariant.

Verification examples:
Existing CONFIRMED: [10:00,11:00)

query [09:00,10:00) → AVAILABLE
query [10:30,11:30) → UNAVAILABLE
query [11:00,12:00) → AVAILABLE

Accepted semantics:
Intervals are half-open: [start,end).

Tady musí být jasné co znamená překryv a které stavy Resource skutečně blokují. Jinak může mít požadavek, diagram, implementace a test každý jiný význam.

6. Podrobný referenční příklad — Confirm Reservation

Ukázka specifikace je záměrně anglicky.

## OP-03 — Confirm Reservation

Goal / user value:
A valid DRAFT Reservation becomes the accepted allocation of Resource.

Trigger:
Authorized User requests confirmation of Reservation X.

Observable requirements:
REQ-03:
The system shall confirm a DRAFT Reservation only when its Resource
is active and its interval does not conflict with an existing
CONFIRMED Reservation of the same exclusive Resource.

REQ-04:
For concurrent confirmation attempts that conflict under BR-02,
at most one Reservation shall reach CONFIRMED.

Preconditions:
- Reservation exists.
- Reservation.state = DRAFT.

Success postcondition:
- Reservation.state = CONFIRMED;
- the Reservation blocks its Resource for its interval;
- BR-02 remains true.

Failure outcomes:
- inactive Resource → reject; Reservation remains DRAFT;
- overlap exists → reject; Reservation remains DRAFT;
- invalid source state → reject; state unchanged.

Verification examples:
DRAFT + active Resource + no overlap → CONFIRMED
DRAFT + overlap → rejected, remains DRAFT
two concurrent conflicting confirmations → at most one CONFIRMED
Tady už souběh není jen implementační detail. Pokud může rozhodnout, zda vznikne dvojí rezervace stejného Resource, patří jeho pozorovatelný výsledek do specifikace. Jak jej zajistí architektura, bude téma C03.

7. Podrobný referenční příklad — Cancel Reservation

Ukázka specifikace je záměrně anglicky.

## OP-04 — Cancel Reservation

Goal / user value:
An eligible Reservation can be withdrawn and stops blocking Resource.

Observable requirement — EXAMPLE POLICY:
REQ-05:
The system shall allow a DRAFT or CONFIRMED Reservation to be
cancelled before its start time.

Preconditions:
- Reservation exists.
- Reservation.state ∈ {DRAFT, CONFIRMED}.
- currentTime < Reservation.start.

Success postcondition:
- Reservation.state = CANCELLED;
- Reservation no longer blocks Resource availability.

Failure outcomes:
- already CANCELLED → [team decides: idempotent success OR explicit rejection];
- start time reached/passed → reject;
- Cancel races with Confirm → team defines accepted observable outcome.

Verification examples:
DRAFT before start → CANCELLED
CONFIRMED before start → CANCELLED and Resource becomes available
CONFIRMED at/after start → rejected according to accepted policy
Toto je referenční pravidlo, ne povinné business pravidlo. Tým musí zvolit logickou politiku rušení pro svou doménu a potom ji používat ve všech pohledech a testech. Pokud pracujete s formulací „před začátkem“, určete dostatečně přesně časovou hranici a zdroj času, aby šla podmínka ověřit.

8. Definujte společná doménová pravidla a invarianty pouze jednou

Minimálně zachyťte pravidla, která platí napříč více operacemi.

BR-01 — Interval semantics
Reservation intervals use [start,end) semantics.

BR-02 — Exclusive Resource invariant
At no committed system state may two CONFIRMED Reservations overlap
for the same exclusive Resource.

BR-03 — Cancellation policy
[team-defined, domain-specific accepted policy]

BR-04 — Domain-specific rule from C01
[team-defined]

Pokud vaše doména používá kapacitní Resource místo exkluzivního, nahraďte BR-02 odpovídajícím pravidlem o kapacitě a zdůvodněte to.

11. Vytvořte / přegenerujte aplikaci podle baseline v0.1

Použijte AI libovolně. Vytvořte jednoduchou spustitelnou aplikaci, ve které lze demonstrovat všechny čtyři základní operace. Uživatelské rozhraní není povinné — API, příkazová řádka nebo jiný reprodukovatelný interface stačí.

Architektura může být v této fázi jednoduchá nebo špatná. Cílem je funkční výchozí stav, ne architektonická dokonalost.

Pro každou operaci skutečně spusťte alespoň:

  • jeden úspěšný příklad;
  • jeden relevantní negativní nebo hraniční příklad.

Pokud aplikace neodpovídá specifikaci, nerozhodujte automaticky, že „kód je špatně“. Určete, zda je problém ve specifikaci, příkladu ověření nebo implementaci, a opravte správný zdroj.

Goal

C01 established which reservation system you are building. C02 specifies and accepts its complete minimum behavior: create a reservation, check availability, confirm the reservation, and cancel it.

The result is not merely “a requirements document”. It is a specification the team understands and owns, plus a simple AI-generated running application whose behavior matches it.

C03 starts from this application and addresses its architecture. Do not optimize code structure prematurely in C02.

Learning outcome: AI may propose requirements, diagrams, tests and code. Engineering ownership means the team can explain for every accepted requirement what it means, why it is needed, under which conditions it applies, what would falsify it, and how satisfaction is demonstrated.
CP1 connection: C02 primarily builds Requirements + Evidence. C03 adds Architecture and turns the running baseline into a defensible walking skeleton. CP1 is frozen after C03 and reviewed during C04.

C02 assumes C01 is complete. Do not recreate C01 outputs.
